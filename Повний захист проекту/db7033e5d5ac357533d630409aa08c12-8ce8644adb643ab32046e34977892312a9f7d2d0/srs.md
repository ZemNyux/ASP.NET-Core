## 1. Вступ

### 1.1. Мета документа

Документ визначає повний набір функціональних та нефункціональних вимог до системи **OLX NextGen** і слугує єдиним джерелом правди (*single source of truth*) для команд розробки, QA, дизайну та продукту на етапах планування, реалізації, приймального тестування та подальшої підтримки.

### 1.2. Обсяг продукту

OLX NextGen — оновлена версія платформи OLX.ua з фокусом на мобільний досвід (PWA-first), персоналізацію на основі ML та розширену монетизацію. Ключові напрямки:

- Швидкий, персоналізований інтерфейс з акцентом на Core Web Vitals
- AI-рекомендації оголошень та автоматична категоризація
- Розширена система монетизації (буст, підписки, преміум-розміщення)
- Посилена безпека, антифрод та стабільність під піковим навантаженням

### 1.3. Аудиторія документа

Product Managers, Engineering Leads, Backend/Frontend/ML-інженери, QA Engineers, DevOps, Security, UX/UI-дизайнери, зовнішні аудитори (security/compliance).

### 1.4. Визначення, акроніми, скорочення

## 2. Загальний опис

### 2.1. Перспектива продукту

OLX NextGen — еволюційний розвиток поточної платформи OLX.ua, а не продукт «з нуля». Міграція відбувається поетапно (feature flags, canary release), без даунтайму для існуючих користувачів.

### 2.2. Класи користувачів та привілеї

| Роль | Опис | Ключові дозволи |
|---|---|---|
| Гість | Неавторизований відвідувач | Перегляд, пошук оголошень |
| Приватний користувач | Фізична особа, продавець/покупець | Публікація до N оголошень, чат, обране |
| Бізнес-користувач | Магазини, автосалони, агентства нерухомості | Безліміт оголошень, аналітика, API-доступ, 2FA обов'язково |
| Модератор | Внутрішній співробітник | Перегляд черги модерації, блокування контенту |
| Адміністратор системи | Технічний персонал | Повний доступ до конфігурації, логів, ролей |

### 2.3. Операційне середовище

| Компонент | Специфікація |
|---|---|
| Браузери | Chrome, Safari, Firefox, Edge — 2 останні мажорні версії |
| Мобільні ОС | iOS 15+, Android 10+ |
| Інфраструктура | AWS / GCP, Kubernetes (EKS/GKE) |
| Дані | PostgreSQL (primary store), Redis (кеш/сесії), Elasticsearch (пошук) |
| Мови інтерфейсу | Українська (основна) · Англійська (uk-UA / en-US) |

> **Примітка щодо мовної локалізації.** Питання наявності російськомовної версії інтерфейсу винесено за межі цього документа й потребує окремого рішення на рівні продуктового та юридичного керівництва з урахуванням чинного законодавства України щодо застосування мов у сфері обслуговування споживачів.

### 2.4. Обмеження дизайну та реалізації

| Шар | Технологія | Обґрунтування |
|---|---|---|
| Frontend | React 19+ / Next.js (App Router) | SSR/SSG для Core Web Vitals, існуюча експертиза команди |
| Backend | Node.js (BFF) + Python / FastAPI (ML-сервіси) | Розділення бізнес-логіки та ML-інференсу |
| ML | TensorFlow / PyTorch, обслуговування через окремий inference API | Ізоляція ML-циклу релізів від основного бекенду |
| БД | PostgreSQL (без міграції на іншу СУБД) | Збереження існуючих даних та операційної експертизи |

### 2.5. Припущення та залежності (Assumptions & Dependencies)

| № | Опис | Тип | Вплив у разі порушення |
|---|---|---|---|
| A-01 | Платіжні провайдери LiqPay/Fondy надають стабільний SLA ≥ 99.9% та sandbox-середовище для тестування | Зовнішня залежність | Блокування FR-10, FR-11 |
| A-02 | ML/Data Science команда доступна для тюнінгу рекомендаційної моделі протягом усього циклу розробки | Внутрішня залежність | Затримка FR-05, FR-08 |
| A-03 | Push-провайдер (FCM/APNs) підтримує заявлені обсяги сповіщень | Зовнішня залежність | Блокування FR-17 |
| A-04 | Історичні дані користувачів (поведінкові, транзакційні) доступні у достатньому обсязі для навчання ML-моделі | Дані | Зниження якості рекомендацій (FR-08) |
| A-05 | Існуюча схема PostgreSQL не потребує breaking changes | Технічне припущення | Ризик для термінів релізу |

## 3. Межі проєкту

### 3.1. У межах проєкту (In Scope)

Усе, що описано в розділах 4 та 6 цього документа.

### 3.2. Поза межами проєкту (Out of Scope)

- Повна переробка бренд-дизайну (rebranding) — лише UI-модернізація в межах поточного brand guideline
- Власна платіжна система (еквайринг) — використовуються виключно сторонні провайдери (LiqPay/Fondy)
- Нативні мобільні застосунки (iOS/Android) — фокус лише на PWA
- Міжнародна експансія за межі України
- Заміна основної СУБД (PostgreSQL) чи міграція на мікросервісну архітектуру «з нуля»

## 4. Функціональні вимоги

*Формат: **[Пріоритет MoSCoW]** ID — Опис → Критерій прийняття (Acceptance Criteria)*

### 4.1. Авторизація та реєстрація

**[Must] FR-01** — Реєстрація через email/телефон + пароль, або через Google/Facebook OAuth 2.0.
→ *AC:* Пароль відповідає політиці (мін. 8 символів, цифра, спецсимвол); підтвердження email/SMS протягом 5 хв; помилки валідації показуються inline.

**[Must] FR-02** — Двофакторна автентифікація (2FA, TOTP або SMS) обов'язкова для бізнес-акаунтів.
→ *AC:* Без активації 2FA бізнес-акаунт не отримує доступу до розширеної аналітики та API.

**[Must] FR-03** — Відновлення пароля через email/SMS.
→ *AC:* Токен відновлення дійсний 15 хв, одноразовий, інвалідується після використання.

### 4.2. Публікація оголошення

**[Must] FR-04** — Створення оголошення з медіа (до 20 фото, 1 відео до 60 с, формати JPEG/PNG/MP4, ≤ 20 МБ/файл).
→ *AC:* Валідація формату/розміру на клієнті до завантаження; прогрес-бар завантаження; graceful fallback при втраті з'єднання.

**[Should] FR-05** — Автоматична категоризація та підказки тегів через ML-модель.
→ *AC:* Точність автокатегоризації ≥ 90% на валідаційному датасеті; користувач може вручну змінити категорію в 1 клік.

**[Should] FR-06** — Преміум-опції: підняття, топ-позиція, кольорове виділення.
→ *AC:* Ефект опції застосовується протягом ≤ 60 с після оплати; статус опції видно в кабінеті користувача.

### 4.3. Пошук та рекомендації

**[Must] FR-07** — Розширений пошук з фільтрами (ціна, регіон, стан товару, спосіб доставки).
→ *AC:* Час відповіді пошукового запиту (Elasticsearch) ≤ 300 мс при p95; комбінація ≥ 5 фільтрів одночасно.

**[Must] FR-08** — Персоналізований блок «Для вас» на головній сторінці на основі ML-рекомендацій.
→ *AC:* CTR блоку ≥ baseline + 15% протягом перших 3 місяців після релізу (A/B-тест); fallback на популярні оголошення при відсутності даних про користувача (cold start).

**[Should] FR-09** — Збереження пошукових запитів та сповіщення про нові відповідні оголошення.
→ *AC:* Сповіщення надсилається ≤ 10 хв після публікації відповідного оголошення.

### 4.4. Монетизація

**[Must] FR-10** — Оплата преміум-пакетів через LiqPay/Fondy (картки, Apple Pay, Google Pay).
→ *AC:* Успішність транзакцій ≥ 98%; повна відповідність вимогам PCI DSS SAQ A (дані картки не потрапляють на сервери OLX).

**[Must] FR-11** — Буст оголошень на термін від 1 до 30 днів.
→ *AC:* Точний відлік терміну дії; автоматичне повідомлення за 24 год до завершення буста.

**[Should] FR-12** — Підписки для бізнес-користувачів (безліміт оголошень, розширена аналітика).
→ *AC:* Автоматичне поновлення підписки з можливістю відключення в один клік; email-нагадування за 3 дні до списання.

### 4.5. Модерація та антифрод

**[Must] FR-13** — Автоматична попередня модерація на основі ML (виявлення спаму, дублікатів, забороненого контенту).
→ *AC:* Recall на тестовому наборі відомих порушень ≥ 95%; false positive rate ≤ 3%.

**[Must] FR-14** — Ручна модерація критичних категорій (авто, нерухомість).
→ *AC:* SLA модерації ≤ 4 год для 95% оголошень у робочий час.

**[Must] FR-15** — Блокування акаунтів за порушення з обов'язковим поясненням причини та механізмом апеляції.
→ *AC:* Користувач отримує сповіщення з кодом причини блокування; апеляція розглядається протягом 48 год.

### 4.6. Мобільний досвід (PWA)

**[Should] FR-16** — Офлайн-режим: перегляд раніше завантажених/збережених оголошень без мережі.
→ *AC:* Service Worker кешує останні 50 переглянутих оголошень; коректний UI-стан «офлайн».

**[Should] FR-17** — Push-сповіщення про нові повідомлення та відповідні оголошення.
→ *AC:* Доставка сповіщення ≤ 30 с після події при активному з'єднанні пристрою.

## 5. Use Cases

### UC-01: Публікація оголошення з AI-підказками категорії

| | |
|---|---|
| **Актор** | Приватний користувач |
| **Передумови** | Користувач авторизований |
| **Основний потік** | 1. Користувач натискає «Створити оголошення» → 2. Завантажує фото/відео → 3. Система пропонує категорію та теги (FR-05) → 4. Користувач підтверджує або редагує → 5. Заповнює опис і ціну → 6. Публікує |
| **Альтернативний потік** | 3a. ML-сервіс недоступний → система показує ручний вибір категорії без блокування публікації |
| **Постумови** | Оголошення потрапляє в чергу автомодерації (FR-13) |

### UC-02: Оплата бустингу оголошення

| | |
|---|---|
| **Актор** | Приватний або бізнес-користувач |
| **Передумови** | Оголошення вже опубліковане й пройшло модерацію |
| **Основний потік** | 1. Користувач обирає «Підняти оголошення» → 2. Обирає термін (1–30 днів) → 3. Обирає спосіб оплати → 4. Підтверджує оплату через LiqPay/Fondy → 5. Отримує підтвердження |
| **Альтернативний потік** | 4a. Платіж відхилено → користувач бачить причину та може повторити спробу |
| **Постумови** | Оголошення отримує пріоритет у видачі згідно з FR-11 |

### UC-03: Блокування акаунту за порушення

| | |
|---|---|
| **Актор** | Модератор, Система (автомодерація) |
| **Передумови** | Виявлено порушення правил платформи |
| **Основний потік** | 1. Система/модератор фіксує порушення → 2. Акаунт блокується з фіксацією причини (FR-15) → 3. Користувачу надсилається сповіщення з поясненням → 4. Користувач може подати апеляцію |
| **Постумови** | Апеляція потрапляє в чергу розгляду підтримки, SLA 48 год |

| ID | Вимога | Ціль | Метод перевірки |

### 6.2. Надійність та доступність

| ID | Вимога |
|---|---|
| NFR-05 | Uptime 99.9% на місяць (SLA), виключаючи заплановані технічні вікна |
| NFR-06 | RTO < 15 хв, RPO < 5 хв для основної БД (PostgreSQL) та пошукового індексу (Elasticsearch) |
| NFR-07 | Graceful degradation: при недоступності ML-сервісу рекомендацій система показує fallback-контент без падіння основного функціоналу |

### 6.3. Безпека

| ID | Вимога |
|---|---|
| NFR-08 | Захист від OWASP Top 10 (SQLi, XSS, CSRF, SSRF, Broken Access Control тощо) на рівні WAF + код-рев'ю |
| NFR-09 | Шифрування персональних даних at rest (AES-256) та in transit (TLS 1.3) відповідно до Закону України № 2297-VI та GDPR (для користувачів з ЄС) |
| NFR-10 | Незалежний пентест зовнішнім підрядником — щоквартально, з обов'язковим усуненням критичних вразливостей протягом 14 днів |
| NFR-11 | Обробка платежів відповідає PCI DSS SAQ A: дані картки не зберігаються і не проходять через інфраструктуру OLX |
| NFR-12 | Rate limiting на автентифікаційних ендпоінтах: не більше 5 невдалих спроб входу за 15 хв з IP/акаунта |
| NFR-13 | Підтримка права на видалення персональних даних («право на забуття») протягом 30 днів з моменту запиту |

### 6.4. Масштабованість

### 6.5. Інтерфейс та доступність

| ID | Вимога |
|---|---|
| NFR-16 | Адаптивний дизайн для екранів від 320 px до 4K |
| NFR-17 | Відповідність WCAG 2.1 рівня AA (контраст, keyboard navigation, screen reader support) |

### 6.6. Якість і тестування

| ID | Вимога |
|---|---|
| NFR-18 | Покриття автотестами (unit + integration) > 80% критичних бізнес-шляхів |

## 7. Ризики

| ID | Ризик | Ймовірність | Вплив | Стратегія мітигації |
|---|---|---|---|---|
| R-01 | ML-модель рекомендацій не досягає цільового CTR через недостатню якість даних | Середня | Високий | Поетапний rollout з A/B-тестуванням, fallback-логіка (FR-08) |
